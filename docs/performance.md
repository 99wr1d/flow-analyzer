# Производительность на длинных матчах (этап 17) и экспорт с рисунками (этап 18)

Раздел «Экспорт с рисунками (этап 18)» ниже мерился отдельным скриптом без окна приложения (`npm run bench:export`). Остальные замеры сделаны в настоящем приложении (Electron, окно за пределами экрана) скриптом `npm run bench`
(`tests/bench/bench.spec.ts`). Порядок работы: измерить → исправить настоящие узкие места → измерить снова. Колонка «до» — сборка
0.14.0 с добавленными только тестовыми функциями замера; «после» — 0.15.0. Время в страницах мерится изнутри (`performance.now`),
чтобы в числа не попадали задержки Playwright. Сырые результаты — JSON, который пишет `npm run bench` (`FLOW_BENCH_OUT`).

## Видео для замеров (`scripts/make-bench.mjs`)

- `bench-1080p-90min.mp4` — 1920×1080, 25 к/с, H.264 (yuv420p, GOP 50), ~3 Мбит/с, AAC (синус), подвижная картинка testsrc2 с таймкодом; 2,1 ГБ.
- `bench-4k-10min.mp4` — 3840×2160, 25 к/с, H.264, ~12 Мбит/с, 10 минут; 0,8 ГБ.
- Вариант с переменной частотой кадров (`vfr`) в скрипте есть, но в замерах не использован.

Проект для замеров масштаба: 2000 эпизодов (9 тегов, оценки, заметки) и 500 рисунков (экранные и на поле, 20 с ключевыми кадрами);
файл проекта 0,9 МБ. Библиотека: 200 проектов, ссылающихся на 90-минутное видео.

Подборка раньше открывала одно видео с перемоткой к первому эпизоду и **декодировала всё до последнего** (здесь 4855 секунд ради 200

читаются одним куском, дальние — отдельными входами ffmpeg с быстрой перемоткой (`-ss` перед `-i`), не больше 24 входов за запуск
(при сотнях эпизодов куски склеиваются по самым маленьким пропускам). Кодирование по-прежнему одно, склейка фильтром `concat`,
поэтому точность до кадра и синхронизация звука сохраняются (проверено настоящим ffmpeg: кадры подборки совпадают с кадрами
исходника, писк на нужной секунде ±0,05 с, длительности звука и видео различаются меньше 0,1 с).

Экспорт с рисунками (всё видео, подборка) ускорен на этапе 18, см. раздел «Экспорт с рисунками (этап 18)» ниже.

## Экспорт с рисунками (этап 18)

Цель: 90-минутный матч «Всё видео целиком» с рисунками — не дольше 15 минут на этой машине (не меньше 150 кадров/с), подборка с рисунками не декодирует
лишнего, качество и точность до кадра прежние. Было около 58 минут (39–46 кадров/с).

Замеры идут без окна приложения: `npm run bench:export` (`tests/bench/exportJob.bench.ts`) вызывает тот же `runExportJob`, что и приложение,
на 90-минутном `bench-1080p-90min.mp4` (1080p, 25 к/с, H.264 около 3 Мбит/с, AAC). Рисунки: **40 на 90 минут** — обычные отрезки по 3 с, «под игроками»
(ключ «газон»), стоп-кадры по 2 с, лупа, три движущихся рисунка с покадровыми PNG (по два слоя). Для замеров «как было» взят отрывок 10 минут с теми же
40 рисунками (в 4 раза плотнее) и пересчёт на 90 минут: граф стоит столько же на каждом кадре, поэтому время растёт линейно.
Сырые результаты — строки JSON (`FLOW_BENCH_OUT`).

### Профиль: где уходило время

Один процесс ffmpeg, 1080p25, кадров в секунду (чем больше, тем лучше). «Декодирование» — `-f null`, остальное добавляется к нему.

| Что считается                                                                                 | к/с              |
| --------------------------------------------------------------------------------------------- | ---------------- |
| Декодирование H.264 (процессор)                                                               | 2700–3400        |
| + `format=yuv420p` + чётный размер кадра                                                      | 2700             |
| + кодирование x264 (veryfast, CRF 20)                                                         | 376–411          |
| + кодирование NVENC p5, tune hq (первая попытка)                                              | 355–387          |
| + кодирование NVENC p4, tune hq, vbr cq 23, aq (выбрано)                                      | 597              |
| Наложение статичной PNG (`overlay`, окно включено / выключено)                                | 1546 / 1732      |
| `trim` + `setpts` + `concat` + чётный размер (граф без рисунков)                              | 2069             |
| Ряд PNG-кадров анимации (замер на одной зацикленной PNG: настоящие кадры ещё и декодируются)  | 349              |
| **Ключ «газон»: только маска** (`chromakey`), на каждом кадре                                 | **65**           |
| **«Под игроками» целиком** (split, маска, overlay, maskedmerge)                               | **60**           |
| **Лупа с `geq`** (было)                                                                       | **78**           |
| Лупа без `geq` (контроль) / лупа с маской-кругом (стало)                                      | 1124 / 446       |
| Аппаратное декодирование `-hwaccel d3d11va` / `cuda` (только декодирование; процессор — 3417) | 847 / 1016       |
| **Весь граф «как было»** (40 рисунков), отрывок 10 минут / пересчёт на 90 минут               | **39–46** / ≈ 40 |

Разбор маски по шагам: `format=rgb24` 1177 к/с, `scale=out_range=pc` 995, `format=yuva444p` 463, `chromakey` **64**. То есть почти всё время
уходит на сам `chromakey` (около 15 мс на кадр 1080p): он работает в один поток (`-filter_threads` и `-filter_complex_threads` не помогают) и считает
маску для **каждого** кадра видео, даже там, где рисунков нет, потому что граф был один на весь результат.

Узкие места по убыванию вклада:

1. **Один общий граф на всё видео.** Маска газона, лупа и наложения считались на каждом кадре, а не только там, где рисунки видны (около 60 и 78 к/с вместо 400).
2. **Один процесс.** Фильтры работали в одном потоке: ключ «газон» не использовал остальные ядра.
3. **`geq` в лупе** (78 к/с): пересчёт каждого пикселя линзы на каждом кадре.
4. **Подборка с рисунками читала всё от первого эпизода до последнего** (граф один, вход один).

Не узкие места: декодирование (не меньше 2700 к/с; аппаратное декодирование медленнее процессорного, потому что кадры всё равно возвращаются в память для
фильтров, поэтому не используется), наложение статичных PNG, склейка `concat`. Кодирование — граница для обычных кадров (около 400 к/с у x264).

### Что сделано

- **Куски** (`exportChunks.ts`, `chunked.ts`, `audioGraph.ts`): результат режется на куски по границам рисунков, каждый кодирует свой процесс ffmpeg со
  своим входом (`-ss`/`-t`), потом куски склеиваются `concat` без перекодирования, а звук (один процесс, параллельно) подмешивается в конце.
  В куске без рисунков нет ни наложений, ни ключа «газон», ни лупы; куски с рисунками идут по нескольку сразу, обычные — не больше двух (у NVENC тяжёлых сразу до трёх: третий сеанс дал +23 % на самом плотном случае)
  (кодер сам занимает все ядра: 6 процессов x264 рядом давали 254 к/с против 334 у одного — измерено). Подборка читает только свои секунды.
- **Кодер видеокарты** (`encoders.ts`): NVENC / Quick Sync / AMF; проверка один раз за запуск настоящим кодированием секунды видео; «Авто» при любой
  неудаче повторяет весь экспорт на x264. На этой машине работает NVENC.
- **Лупа без `geq`** (`loupe.ts`): маска-круг на один кадр (`geq` один раз) и `alphamerge` вместо `geq` на каждый кадр: 78 → 446 к/с.
- **Ряд кадров анимации** (`drawGraph.ts`): шкала времени ряда — микросекунды (`settb`), сдвиг на четверть кадра раньше; в конец ряда кладётся
  прозрачная картинка (`blankPng.ts`). Без этого последний кадр анимации терял рисунок, если начало куска не лежит на кадре (`overlay` держит картинку
  только до её метки времени, а `setpts` в шкале 1/25 округлял сдвиг на долю кадра до целого кадра).
- Не сделано: аппаратное декодирование (медленнее, см. профиль); одновременный экспорт нескольких клипов «Отдельных файлов»
  (каждый клип — отдельный запуск, как раньше; для коротких клипов выигрыш от кусков съедается запуском процессов).

\* «Как было» для 90 минут — пересчёт с отрывка 10 минут; прямой замер «как было» на всех 90 минутах (около часа) не делался. Подборка «как было» измерена

Цель выполнена с запасом: **6,1 минуты на процессоре и 3,7 минуты на видеокарте против 15 минут по заданию**. «Всё видео» с рисунками теперь
быстрее, чем «Всё видео» без рисунков одним процессом (6,1 против 8,4 мин): куски идут параллельно и не тратят время на `+faststart` для каждого файла.
Подборка с рисунками ускорилась в 69 раз на процессоре и в 98 раз на видеокарте.

**Самый плотный случай** — рисунки на каждом кадре (40 рисунков за 2 минуты, видео 2 минуты, `FLOW_BENCH_MINUTES=2`): было 36–38 к/с, стало
96 к/с на процессоре и 113 к/с на видеокарте (3 сеанса NVENC; на двух — 92). Выигрыш здесь только 2,5–3 раза, потому что тяжёлые фильтры
(маска газона, лупа, наложения) работают на каждом кадре и упираются в однопоточный `chromakey`; кусков с рисунками идёт несколько сразу, но не больше, чем ядер и сеансов.
Реальный матч с десятками рисунков лежит между этим случаем и «40 на 90 минут».

**Тот же замер в самом приложении** (`npm run bench`, часть «экспорт»; окно, настоящие рисунки из проекта, «Авто» = видеокарта):

| Показатель                                                             | Этап 17      | Этап 18                                         |
| ---------------------------------------------------------------------- | ------------ | ----------------------------------------------- |
| 10 отдельных клипов по 10 с, точно: время / к/с                        | 12,8 с / 195 | 8,2 с / 303                                     |
| Подборка из 20 эпизодов по 10 с на 90 минут, без рисунков: время / к/с | 16 с / 314   | 10,3 с / 485                                    |
| «Всё видео», отрывок 2 минуты, 40 рисунков: время / к/с                | 78,9 с / 38  | 39,8 с / 75 (в том числе подготовка PNG в окне) |

Что осталось узким местом: на обычных кадрах — само кодирование (x264 veryfast около 400 к/с на 12 потоках; NVENC p4 около 600 к/с), на кадрах с рисунками
«под игроками» — `chromakey` (около 65 к/с на один поток, но таких кадров немного и кусков с ними идёт несколько сразу — на видеокарте до трёх). У коротких клипов (10 секунд)
время почти целиком уходит на запуск процессов и перемотку (около 2 с на клип), поэтому видеокарта там мало помогает.

### Качество: SSIM против исходника

`node scripts/encoder-quality.mjs <видео> <начало> <секунд>`: отрывок кодируется теми же параметрами, что и экспорт, и сравнивается с исходным. Требование —
SSIM аппаратного кодера не ниже 0,97 и не хуже x264.

| Видео                                        | x264 CRF 20: SSIM / PSNR / файл | NVENC p4 hq cq 23 aq: SSIM / PSNR / файл |
| -------------------------------------------- | ------------------------------- | ---------------------------------------- |
| bench-1080p-90min.mp4, 20 с с 1200-й секунды | 0,99733 / 47,4 дБ / 10,6 МБ     | **0,99872** / 51,3 дБ / 17,1 МБ          |
| players.mp4 (шумная трава), 4 с              | 0,97699 / 46,0 дБ               | 0,97929 / 46,7 дБ                        |
| pitch.mp4, 4 с                               | 0,99828 / 53,3 дБ               | 0,99942 / 59,1 дБ                        |
| sample.mp4, 4 с                              | 0,99347 / 34,3 дБ               | 0,99491 / 34,4 дБ                        |

NVENC при таком качестве даёт файл в 1,5–1,7 раза больше (на отрывке 10,6 → 17,1 МБ). Параметр подобран по SSIM: cq 25 давал на шумной картинке 0,9715
(ниже x264), поэтому взят cq 23. Intel Quick Sync и AMD AMF в сборке есть, но на этой машине такого железа нет: их параметры не проверялись на качество
и скорость; если кодер не заведётся, проверка при запуске его отбросит и экспорт пойдёт на процессоре.

## Что изменено ради скорости

1. **Список эпизодов** (`EpisodeList.tsx`, `windowing.ts`): при больше 100 эпизодах в DOM лежат только строки около видимой области,
   остальное — пустое место нужной высоты (высоты уточняются по измерению). Строки мемоизированы и не подписаны на хранилище.
   Кнопки оценки больше не ищут свой эпизод в списке из 2000 (6000 поисков на каждое изменение — главная причина 300 мс на тег).
2. **Дорожка эпизодов** (`EpisodeTrack.tsx`): полосы мемоизированы — при добавлении эпизода или смене выбранного перерисовываются
   только изменившиеся.
3. **Бегунок таймлайна**: двигается через `transform` на своём слое, а не через `left: %`; раньше каждый кадр воспроизведения
   перерисовывал тысячи полос под ним (отсюда потерянные кадры и долгие задачи при большом проекте).
4. **Подборка** (`chunks.ts`, `args.ts`): куски чтения вместо декодирования всего отрезка (см. выше).
5. **Библиотека** (`cards.ts`): кэш сводок проектов по размеру и времени файла.
6. **Журнал**: долгие сохранение и открытие проекта (от 300 мс) записываются в журнал со временем (без названий и содержимого).

## Как повторить

```bash
node scripts/make-bench.mjs <папка> all                               # видео (≈ 10 минут генерации, ≈ 3 ГБ)
FLOW_BENCH_DIR=<папка> FLOW_BENCH_LABEL=after npm run bench           # все замеры (≈ 30 минут)
FLOW_BENCH_DIR=<папка> FLOW_BENCH_ONLY=scale,export npm run bench     # часть замеров
```

Экспорт с рисунками (этап 18):

```bash
node scripts/make-bench.mjs <папка> long                                   # bench-1080p-90min.mp4, около 4 минут
FLOW_BENCH_DIR=<папка> FLOW_BENCH_OUT=<файл.jsonl> npm run bench:export   # все случаи (около 1,5 часа; последний, «как было», около 40 минут)
FLOW_BENCH_DIR=<папка> FLOW_BENCH_CASES=whole-gpu-chunks npm run bench:export
node scripts/encoder-quality.mjs <видео> 1200 20                           # SSIM и скорость x264 и NVENC на отрывке
```

Случаи: `<что>-<кодер>-<способ>`, где что = `whole` | `compilation` | `clips` | `plain`, кодер = `cpu` | `gpu`, способ = `mono` (один процесс, как раньше) | `chunks`.
`FLOW_BENCH_MINUTES` — длина «всего видео» (по умолчанию 90). Нужно место: куски и итоговый файл — по 3–5 ГБ на 90 минут.

Переменные: `FLOW_BENCH_OUT` (файл результатов), `FLOW_BENCH_PLAY_SEC` (длина воспроизведения, 60), `FLOW_BENCH_SOAK_MIN` (10),
`FLOW_BENCH_EXCERPT_SEC` (отрывок для экспорта с рисунками, 120). Большие файлы держите вне репозитория и удаляйте после замеров.
Во время замера не запускайте другие тяжёлые задачи (сборку, тесты): они искажают числа. Чтобы Windows не уходила в сон,
не оставляйте компьютер без дела на время длинного замера.

Дата замера: 2026-10-21. Выкидной спайк вне репозитория (`…\scratchpad\spike\`, `onnxruntime-node` 1.30, `onnxruntime-web` 1.30 в окне Electron 44 / Chromium 152). Машина: Ryzen 5 7500F, RTX 5060 Ti (драйвер 32.0.16.1088), Windows 11 с включённым Smart App Control. Видео: «EVERY Champions League Goal From Matchday 2» (720p, 25 к/с), 250 кадров = 10 с. ### Связывание рамок (IoU + центр + цветовая гистограмма) на 10 моментах

Начальная рамка выбрана вручную по кадру, дальше простое связывание только одного игрока, остановка при разрыве кадра (разница гистограмм > 0,2). Итог лучшего варианта (рамки RF-DETR Small): удержал до конца или честно остановился с понятной причиной — 7 из 10 (3 остановки на смене плана, все верные), 2 преждевременные остановки в толпе, 1 перепрыгивание (на судью/соперника из-за того, что при старте рамки двух игроков перекрывались). Без цветовой гистограммы — 4 перепрыгивания из 10. Без разрыва кадра связывание после смены плана продолжало бы вести чужого игрока (моменты 8 и 10). Порог ТЗ «ни одного перепрыгивания, ≥ 8 из 10» на этом простом варианте не достигнут; подробности и картинки — в `report.md` спайка.

### Рекомендация

Пара: `onnxruntime-web` (WebGPU, запасной путь WASM) в скрытом окне + D-FINE-S COCO (Apache-2.0, 41,5 МБ, fp16 — 21 МБ). Итог по размеру около +69 МБ. Минус: на видеокарте 8,5–14,5 с на 250 кадров, цель «≤ 5 с» достигается только если детектировать каждый 2-й кадр или в окне вокруг игрока; на CPU через WASM 23–70 с в зависимости от входа. Запасной вариант, если нужна скорость и можно +64 МБ только под Windows: `onnxruntime-node` + DirectML и YOLOX-S/RF-DETR Nano (2,6–4,5 с), но тогда для Mac нужен отдельный путь.
