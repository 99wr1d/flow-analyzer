# Производительность на длинных матчах (этап 17)

Замеры сделаны в настоящем приложении (Electron, окно за пределами экрана) скриптом `npm run bench`
(`tests/bench/bench.spec.ts`). Порядок работы: измерить → исправить настоящие узкие места → измерить снова. Колонка «до» — сборка
0.14.0 с добавленными только тестовыми функциями замера; «после» — 0.15.0. Время в страницах мерится изнутри (`performance.now`),
чтобы в числа не попадали задержки Playwright. Сырые результаты — JSON, который пишет `npm run bench` (`FLOW_BENCH_OUT`).

## Машина

| Что                        | Значение                                                                                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Процессор                  | AMD Ryzen 5 7500F, 6 ядер / 12 потоков                                                                                                          |
| Память                     | 32 ГБ                                                                                                                                           |
| Видеокарта                 | NVIDIA GeForce RTX 5060 Ti (драйвер 32.0.16.1088); `app.getGPUInfo('basic')` показал её, но не активной для окна замеров (окно за краем экрана) |
| ОС                         | Windows 11 Pro                                                                                                                                  |
| Electron / Chromium / Node | 44.9.0 / 152.0.7977.167 / 24.22.0                                                                                                               |

Сведения взяты из `os.cpus()`, `os.totalmem()` и `app.getGPUInfo('basic')` (раздел `machine` результатов). Раз GPU в окне замеров
не числилась активной, воспроизведение без потерь кадров получено при том, что картинку, возможно, собирал процессор.
На обычном экране, где GPU работает, запас должен быть больше, но этого я не измерял.

## Видео для замеров (`scripts/make-bench.mjs`)

- `bench-1080p-90min.mp4` — 1920×1080, 25 к/с, H.264 (yuv420p, GOP 50), ~3 Мбит/с, AAC (синус), подвижная картинка testsrc2 с таймкодом; 2,1 ГБ.
- `bench-4k-10min.mp4` — 3840×2160, 25 к/с, H.264, ~12 Мбит/с, 10 минут; 0,8 ГБ.
- Вариант с переменной частотой кадров (`vfr`) в скрипте есть, но в замерах не использован.

Проект для замеров масштаба: 2000 эпизодов (9 тегов, оценки, заметки) и 500 рисунков (экранные и на поле, 20 с ключевыми кадрами);
файл проекта 0,9 МБ. Библиотека: 200 проектов, ссылающихся на 90-минутное видео.

## Результаты

Цели из задания: перемотка p95 < 300 мс; покадровый шаг < 100 мс; тег при 2000 эпизодов < 50 мс; статистика < 300 мс;
сохранение и открытие < 1 с; стартовый экран на 200 проектов < 1 с; без потерь кадров на 1080p при 1×.

### Библиотека: 200 проектов

| Показатель                                                            | До            | После         |
| --------------------------------------------------------------------- | ------------- | ------------- |
| Стартовый экран: 200 карточек видны (от загрузки страницы), мс        | 595           | 488           |
| Запрос списка (IPC, 200 карточек + 1,1 МБ эскизов), среднее / p95, мс | 138 / 155     | 77 / 95       |
| Возврат «Главная» из проекта → 200 карточек, мс                       | 227           | 131           |
| Эскизы: 200 штук подряд (ffmpeg, `-ss` до `-i`), всего / на штуку     | 93 с / 464 мс | 90 с / 450 мс |

Что сделано: сводки проектов кэшируются по пути, размеру и времени изменения файла (повторный показ списка не читает и не
проверяет файлы заново). Проекты в замере маленькие (5–45 эпизодов), поэтому выигрыш скромный; для проектов с тысячами эпизодов
он больше, потому что проверка схемой такого файла занимает десятки миллисекунд.
Цель «стартовый экран < 1 с» выполнена. Эскизы делаются при сохранении проекта в фоне (не блокируют работу), по одному на проект;
450 мс на эскиз почти целиком уходят на открытие 2-гигабайтного файла и чтение его индекса: ключи `-noaccurate_seek`,
`-skip_frame nokey` и `-probesize` я пробовал, выигрыша они не дали (измерено, 417–464 мс), поэтому оставлено как есть.
Эскизы по-прежнему отдаются прямо в ответе на запрос списка (до 200 штук по ≤ 60 КБ), «ленивая» подгрузка по карточкам не делалась:
при 77 мс на запрос она не нужна.

### Экспорт

| Показатель                                                               | До              | После          |
| ------------------------------------------------------------------------ | --------------- | -------------- |
| 10 отдельных клипов по 10 с, точно: время / кадров в секунду кодирования | 13,8 с / 182    | 12,8 с / 195   |
| Подборка из 20 эпизодов по 10 с, разбросанных по 90 минутам: время / к/с | 57–73 с / 70–88 | **16 с / 314** |
| «Всё видео» с 40 рисунками, отрывок 2 мин: время / к/с                   | 79,5 с / 38     | 78,9 с / 38    |
| То же, пересчёт на 90 минут                                              | ≈ 60 мин        | ≈ 59 мин       |

Подборка раньше открывала одно видео с перемоткой к первому эпизоду и **декодировала всё до последнего** (здесь 4855 секунд ради 200
секунд результата). Теперь эпизоды делятся на «куски чтения» (`src/main/ffmpeg/chunks.ts`): эпизоды с пропуском до 12 секунд
читаются одним куском, дальние — отдельными входами ffmpeg с быстрой перемоткой (`-ss` перед `-i`), не больше 24 входов за запуск
(при сотнях эпизодов куски склеиваются по самым маленьким пропускам). Кодирование по-прежнему одно, склейка фильтром `concat`,
поэтому точность до кадра и синхронизация звука сохраняются (проверено настоящим ffmpeg: кадры подборки совпадают с кадрами
исходника, писк на нужной секунде ±0,05 с, длительности звука и видео различаются меньше 0,1 с).

**Не ускорено:** «Всё видео» с рисунками. 38 к/с — это граф с десятками наложений; 90-минутный матч с рисунками кодируется
около часа. Компиляция с рисунками (`planDrawn`) по-прежнему читает весь отрезок от первого до последнего эпизода.
Это известное ограничение: оптимизация графа с рисунками отложена.

### Долгая работа: память

10 минут имитации работы (перемотка, шаги, теги, отмена, статистика, сохранение, воспроизведение; проект с 600 эпизодами
и 100 рисунками, автосохранение каждые 5 с):

| Показатель                                         | До (606 итераций) | После (702 итерации) |
| -------------------------------------------------- | ----------------- | -------------------- |
| Окно (рендерер), МБ: начало → через минуту → конец | 240 → 662 → 777   | 165 → 431 → 537      |
| Всего процессов, МБ: начало → конец                | 693 → 1321        | 625 → 1087           |
| JS-куча, МБ                                        | 26 → 26           | 13 → 13              |

JS-куча не растёт вообще — утечки в коде страницы нет. Рабочий набор окна растёт медленно (около 10 МБ в минуту после первой минуты)
и за 10 минут плато не достиг: похоже на буферы видео и композитора после сотен перемоток по двухгигабайтному файлу, но причину
я не выяснял. Для долгого сеанса (несколько часов) это стоит перемерить.

## Что изменено ради скорости

1. **Список эпизодов** (`EpisodeList.tsx`, `windowing.ts`): при больше 100 эпизодах в DOM лежат только строки около видимой области,
   остальное — пустое место нужной высоты (высоты уточняются по измерению). Строки мемоизированы и не подписаны на хранилище.
   Кнопки оценки больше не ищут свой эпизод в списке из 2000 (6000 поисков на каждое изменение — главная причина 300 мс на тег).
2. **Дорожка эпизодов** (`EpisodeTrack.tsx`): полосы мемоизированы — при добавлении эпизода или смене выбранного перерисовываются
   только изменившиеся.
3. **Бегунок таймлайна**: двигается через `transform` на своём слое, а не через `left: %`; раньше каждый кадр воспроизведения
   перерисовывал тысячи полос под ним (отсюда потерянные кадры и долгие задачи при большом проекте).
4. **Подборка** (`chunks.ts`, `args.ts`): куски чтения вместо декодирования всего отрезка (см. выше).
5. **Библиотека** (`cards.ts`): кэш сводок проектов по размеру и времени файла.
6. **Журнал**: долгие сохранение и открытие проекта (от 300 мс) записываются в журнал со временем (без названий и содержимого).

## Как повторить

```bash
node scripts/make-bench.mjs <папка> all                               # видео (≈ 10 минут генерации, ≈ 3 ГБ)
FLOW_BENCH_DIR=<папка> FLOW_BENCH_LABEL=after npm run bench           # все замеры (≈ 30 минут)
FLOW_BENCH_DIR=<папка> FLOW_BENCH_ONLY=scale,export npm run bench     # часть замеров
```

Переменные: `FLOW_BENCH_OUT` (файл результатов), `FLOW_BENCH_PLAY_SEC` (длина воспроизведения, 60), `FLOW_BENCH_SOAK_MIN` (10),
`FLOW_BENCH_EXCERPT_SEC` (отрывок для экспорта с рисунками, 120). Большие файлы держите вне репозитория и удаляйте после замеров.
Во время замера не запускайте другие тяжёлые задачи (сборку, тесты): они искажают числа. Чтобы Windows не уходила в сон,
не оставляйте компьютер без дела на время длинного замера.
