# Слежение за игроком — Задача 0: пробный замер (спайк)

> **For agentic workers:** выполняется одним субагентом, выкидной код вне репозитория. По итогам автор дизайна пишет
> основной план `2026-10-2x-player-tracking.md` (задачи 1…N) с выбранными моделью и движком.

**Goal:** выбрать пару «детектор людей + движок запуска» для слежения, измерив скорость, вес и качество на реальном видео.

**Architecture:** отдельная временная папка с собственным `package.json` (не репозиторий). Кадры отрезка декодирует
ffmpeg (из `node_modules/ffmpeg-static` проекта), детектор запускается двумя движками, по найденным рамкам строится
простое связывание (IoU + ближайший центр) для проверки «ведёт ли одного игрока».

**Tech Stack:** Node 24, Electron 44 (из проекта), onnxruntime-web (WebGPU/WASM), onnxruntime-node (DirectML/CPU),
ffmpeg-static.

**Spec:** `docs/superpowers/specs/2026-10-21-player-tracking-design.md`

## Global Constraints

- Лицензии кода и весов: только Apache-2.0 / MIT / BSD. Не брать: Ultralytics YOLO (AGPL), RF-DETR XL/2XL (PML 1.0),
  веса «только для исследований». Для каждого кандидата записать лицензию весов и датасет обучения.
- Источники загрузки — только официальные (GitHub релизы авторов, Hugging Face организации авторов, npm). Каждую
  загрузку класть в свою пустую папку; не запускать скачанные скрипты.
- Видео пользователя — только на месте, только локально: `C:\Users\user\Videos\flow-samples\EVERY Champions League
  Goal From Matchday 2 _ Highlights.mp4` (24:12, 720p, 25 к/с). Кадры/скриншоты — только во временной папке.
- Ничего не менять в `C:\Users\user\projects\flow-analyzer` (там параллельно идёт версия 0.16.4), кроме
  `docs/performance.md` (раздел «Слежение: замер моделей») в самом конце.
- Electron запускать через `env -u ELECTRON_RUN_AS_NODE`. Если Smart App Control блокирует какой-либо файл
  (electron.exe, .node, .dll) — записать это как результат (важно для выбора движка), не обходить.
- Цели из спеки: 10 с видео ≤ 5 с на RTX 5060 Ti, ≤ 60 с на процессоре; находит игроков ростом ~40 px в 720p;
  модели + движок ≈ +50–90 МБ (сверх +100 МБ — отметить).

## Review Focus

- Мелкие игроки на общем плане (40–80 px) — главный риск качества; мерить отдельно.
- Пересечение двух игроков — не перепрыгивает ли простое связывание.
- Смена плана/повтор внутри отрезка — видно ли её по разнице кадров.
- Блокировка нативных DLL Smart App Control — решающий фактор для варианта Б.
- WebGPU в Electron 44 может быть недоступен/выключен в скрытом окне — проверить в окне, как его будет создавать
  программа (фоновое, без фокуса).

- [ ] **Шаг 1: кандидаты.** RF-DETR Nano (Apache-2.0, ONNX-экспорт авторов), YOLOX-S и YOLOX-Tiny (Apache-2.0, ONNX из

- [ ] **Шаг 2: отрезки.** Выбрать 10 моментов по 10 с из видео (разные матчи, общий план, есть пересечения игроков,
  хотя бы 2 с повтором/сменой плана). Декодировать кадры ffmpeg'ом во временную папку (или потоком).
- [ ] **Шаг 3: скорость.** Для каждой модели × движка (onnxruntime-node: DirectML и CPU; onnxruntime-web в окне
  Electron: WebGPU и WASM) — время на 10 с видео (250 кадров), прогрев отдельно, память. Записать, если движок не
  запустился и почему.
- [ ] **Шаг 4: качество.** На 30+ кадрах с общим планом — сколько игроков на поле найдено (сравнить с ручным подсчётом по
  кадру, глядя на изображение), минимальный рост найденного игрока, ложные срабатывания на зрителях/рекламе.
- [ ] **Шаг 5: связывание.** Для лучшей пары на 10 моментах: стартовая рамка = игрок, по которому кликнул бы тренер
  (выбрать глядя на кадр), простое IoU+центр связывание до конца отрезка; посмотреть на 3–4 кадра каждого момента —
  держит ли того же игрока, где теряет, есть ли перепрыгивания. Разница гистограмм соседних кадров — ловит ли смену
  плана.
- [ ] **Шаг 6: итог.** `report.md` + раздел в `docs/performance.md`: таблица скорость/вес/качество, рекомендация
  пары с обоснованием, что не работает. Не коммитить.
